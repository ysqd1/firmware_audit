## 已确认

1. 第一阶段运行单次固件程序或 CGI；常驻网络服务测试后置。
2. 容器常驻改造暂不进行。QEMU 使用沙箱执行环境，必要的文件与执行支撑仍需设计。
3. 允许有明确依据的环境适配，不自动修补与漏洞成立有关的程序逻辑。依据、修改及实验条件必须留档。
4. 探索性假设实验不能单独作为 confirmed 依据；运行失败不作漏洞反证，崩溃不自动确认为漏洞。
5. 第一阶段使用预定义适配模板。Agent 可依据证据自主选择模板和参数；不自由编写替代库/接口代码，遇到不支持的依赖返回明确阻塞。该选择不表示任何模板清单已获确认。
6. 首批模板类别已选：基础模板加有限 NVRAM 配置读取模拟。值有来源、接口明确，未知值不编造；具体接口和 ABI 清单仍待事实核查。
7. 每次实验从干净环境重建，保存脚本、输入、适配方案和历史结果，不自动继承被测程序的运行文件。复用历史文件须显式列为新实验输入并记录来源。
8. QEMU 按证据缺口调用，不要求所有支持架构的二进制候选必跑。受阻时明确说明缺失条件并允许继续静态分析；动态实验不是所有 Finding 的统一前置条件。
9. 独立 QEMU 检查/执行入口，保留 sandbox_verify 脚本实验职责，共享底层隔离、超时和证据能力；具体工具参数待 spec。
10. 初始可配置预算：单次默认 60 秒、上限 180 秒，每个 Analysis Investigation 和每个 Verification Case 分别最多 4 次目标执行。对照、异常测试和复现均计数，受案例总预算约束；失败不自动重试。这些数值尚未实测校准。
11. Q7 A：第一阶段包含原程序启动的有限 shell/辅助程序执行链，仍是单次实验，不扩展常驻网络服务。具体机制需验证，不用宿主 shell 替代固件 shell 后宣称原链路已复现。
12. Q8 A：第一阶段须跑通真实固件的一条单次程序/CGI 业务通路，提供可检查的输入输出、正常输入对照，并在干净环境中重复取得结果；有限 NVRAM 模板另须验证真实接口兼容性。不要求全部案例跑通或命中 GT。

边界记录：[ADR-0013](../../docs/adr/0013-qemu-user-mode-experiment-boundary.md)。术语已补充至 CONTEXT.md。用户同意的是范围和边界，不是下面所有实现选择。

## 第二次设计检查：决定已记录，技术验证尚未完成

已确认决定保持有效。Q7/Q8 已由用户选择 A 并回写 ADR；下列技术约束仍需形成可验证的规格，不能视为已实现。

- 技术约束：现有 sandbox_verify 可运行 Python 等通用脚本，解释器名单不能阻止子进程。若将 QEMU 加入共用镜像，只在专用工具入口计数，则脚本可能绕过目标执行次数及材料记录。必须设计统一受控执行或能力隔离；共用底层代码不意味着必须使用同一镜像。不得仅靠提示词声称预算得到强制执行。
- 技术约束：现有 run_docker 的 TimeoutExpired 分支返回 124，没有显式按容器身份停止/删除的逻辑；新实验路径需要容器及派生进程清理、有限输出与资源限额。此为代码检查，未做运行验证。
- 技术约束：运行副本可写不等于历史证据目录可写。目标只可写当前实验工作区，权威执行记录由 Host 保存；不能把整个世代证据目录作为可写实验盘。
- 已决 Q7 A：将有限的子进程执行链纳入目标范围，仍不启动常驻网络服务、不修改宿主全局 binfmt；先核查可行性，不能用宿主 shell 替换固件 shell 后称原链路已复现。若约束下不可行，回报具体阻塞后再决定收窄范围。
- 已决 Q8 A：要求真实固件单次程序/CGI 在有来源的环境下完成一条可检查通路，并通过正常输入对照与干净环境复现；安装成功、版本输出、合成夹具不单独构成交付完成。有限 NVRAM 模板另有真实接口兼容性验收，不把不同样本各自通过拼成一条完整漏洞链。不要求命中 GT 或所有案例跑通。

只读代码核查补充：`host/budget.py` 当前仅有全局工具次数等预算，没有上述按 Investigation/Verification Case 分开的 QEMU 执行台账。规格须定义计数时点、持久化与恢复，以及一次受控实验内子进程和额外顶层执行的计数边界；不能把一个脚本批量运行多个独立测试算成一次实验。进程数限制与顶层实验名额是不同约束，具体实现不得混为一谈。

函数 ABI、子进程执行机制、具体资源值及验收样本是技术调查任务。未完成的可行性调查应在 spec 中成为后续实现的明确前置条件，不以用户选择代替事实验证。

## 只读事实核查

现有 target/6 和 target/7 抽查的目标 ELF 为 32 位小端 ARM，动态程序使用 `/lib/ld-uClibc.so.0`；target/8 抽查 ELF 为 32 位大端 MIPS，使用 `/lib/ld-musl-mips-sf.so.1`。因此首批支持矩阵建议覆盖 ARM 小端及 MIPS 大端，尚不据此宣称所有 ABI 均兼容。抽查没有执行固件程序，也没有启动容器。

本机 PATH 与现有 Dockerfile 未提供 QEMU 安装证据；未检查容器内可执行文件，所以不声称镜像中绝对不存在 QEMU。实现前须明确镜像版本和依赖，而非依赖宿主全局 binfmt 注册。QEMU 的加载器前缀不能替代文件系统隔离，路径及运行根设置需另作设计。

NVRAM 动态符号核查：target/6 的 `lib/libnvram.so` 包含 `nvram_get/getall/set/unset/commit/init` 等符号；target/7 除该类接口外，`bin/httpd` 还导入 `bcm_nvram_get/match/set/commit`、`envram_get_value/set_value/to_nvram` 等厂商包装接口，不能当作通用 nvram_get 的同义函数。默认配置候选包括 target/6 的 `etc/defnodes/defaultvalue.php`、`etc/defnodes/defaultvalue.xml`，以及 target/7 的 `webroot_ro/nvram_default.cfg`；此轮未读取配置值，路径存在不证明配置适用于当前实验。

target/8 此次扫描未发现上述 NVRAM 动态符号，发现 UCI 配置相关路径；这不能证明不存在任何 NVRAM 使用，但不足以将其列为首批 NVRAM 模板验收样本。动态符号只能支持名称和导入/导出关系，不能证明函数原型、返回值、内存所有权、缺失键语义或运行时存储位置。须核查调用点或 ABI 资料后才能列入支持表；本次没有执行固件、启动容器或读取 GT。QEMU 的 static 打包不是由这些 ELF 事实推导出的强制要求。

# QEMU 用户态固件执行实验第一阶段规格

日期：2026-09-21（同日修订：执行模型升级为会话制，见 [ADR-0013](../../docs/adr/0013-qemu-user-mode-experiment-boundary.md) 会话制确认节）  
依据：[ADR-0013](../../docs/adr/0013-qemu-user-mode-experiment-boundary.md)、[设计访谈](design-discussion.md)、[方案汇总](proposed-design.md) 以及 [CONTEXT.md](../../CONTEXT.md)。

## Problem Statement

Step5 当前可以读取解包树、反编译边车和静态证据，也有 `sandbox_verify` 脚本复核工具，但无法在隔离环境中直接运行固件自带的 ARM 或 MIPS 用户态程序。遇到命令注入、CGI 输入处理、配置驱动行为或依赖运行时条件的疑点时，审计只能停留在静态推断，或者使用与固件环境不一致的脚本替代。

现有脚本工具不能承担这项能力：脚本可以启动任意子进程，而 Host 当前只有全局工具调用预算，没有按 Investigation 和 Verification Case 记录目标执行次数。若把 QEMU 仅作为脚本中的一个命令，执行次数、输入、环境和证据就无法可靠归属。现有 Docker 超时路径也没有为 QEMU 实验定义容器、派生进程和未完成输出的清理语义。

## Solution

在 Docker 沙箱执行环境中提供一个由 Host 控制的专用 QEMU 检查/执行工具。QEMU 用户态模拟器和其版本由镜像固定，宿主 Kali 不需要安装 QEMU，也不依赖宿主全局 binfmt 注册。实验以会话为单位：开启会话时干净重建运行目录，会话内每次执行运行固件原始程序或 CGI 及其有限的 shell/辅助程序执行链，运行目录内的状态跨 ReAct 轮积累；一次性单发实验是只含一次执行的会话特例。会话结束即拆除容器；第一阶段两次执行之间不允许目标进程存活，不启动常驻网络服务或整机模拟。

QEMU 工具与 `sandbox_verify` 共用隔离、超时、输出采集和 Evidence 保存基础，但拥有独立的能力入口。`sandbox_verify` 继续负责 Python、Node、PHP 脚本实验，不能借脚本启动 QEMU 来绕过专用工具的预算和证据台账。每次会话从原始目标和显式声明的适配材料干净重建（会话之间干净、会话之内状态连续），目标只能写当前会话运行目录，不能写权威历史 Evidence。

第一阶段支持有证据依据的预定义环境适配：基础目录、配置文件、argv/环境、标准输入或 CGI 输入，以及有限且 ABI 已核实的 NVRAM 读取模板。适配值必须来自固件材料或其他可核查来源，未知值不能伪造成空值或成功。target/6、target/7 的 NVRAM 包装接口必须分别核实；target/8 当前只作为 UCI/配置路径候选，不预先列入 NVRAM 模板支持表。

QEMU 观察只作为 Evidence，不能直接产生 confirmed Finding。程序正常退出、非零退出、信号、崩溃、超时或启动失败都必须带有明确结果分类和限制说明，由 analysis 提出 Claim、由 verification 独立重建并复核。第一阶段交付的最低门槛是真实固件的一条单次程序或 CGI 业务通路，具备可检查输入输出、正常输入对照、干净环境复现，并完成有限 NVRAM 模板的真实接口兼容性验证。

## User Stories

1. As an 审计运行者, I want 在现有 Step5 工作区中按需运行固件用户态程序, so that 静态证据不足时可以取得真实程序行为。
2. As an 审计运行者, I want 不在 Kali 主机手动安装 QEMU, so that 审计环境由版本化 Docker 镜像重现。
3. As an 审计运行者, I want 首批支持 ARM32 小端和 MIPS32 大端, so that 当前路由器样本可以进入同一执行接口。
4. As an 审计运行者, I want 预检报告架构、解释器和依赖状态, so that 明确知道实验是准备阻塞还是目标运行失败。
5. As an analysis Agent, I want 只在证据缺口适合动态观察时调用 QEMU, so that 动态执行不会成为每个 Candidate 的无条件开销。
6. As a verification Agent, I want 在自己的干净实验目录重新取得关键材料并执行, so that Analysis 的运行结果不会被直接当作独立复核证据。
7. As an 审计工程师, I want QEMU 工具是专用受控入口, so that 模型不能自由拼接命令绕过路径白名单和执行记录。
8. As an 审计工程师, I want `sandbox_verify` 不能启动 QEMU, so that 每个目标执行都有唯一的预算归属和 Evidence 身份。
9. As an 审计运行者, I want 每次会话使用原始固件的只读输入, so that 实验不会修改解包树或历史审计材料。
10. As an 审计运行者, I want 目标可以写独立运行时目录, so that CGI、shell 和辅助程序仍能完成需要临时文件的正常路径。
11. As an 审计复查者, I want 运行目录、适配材料和权威 Evidence 分离, so that 被测程序不能篡改审计记录。
12. As an analysis Agent, I want 能传入程序路径、argv、argv0、工作目录、受控环境和输入文件, so that 单次执行可以表达真实调用条件。
13. As an analysis Agent, I want 有限 shell/辅助程序链沿用固件中的程序和库, so that 命令注入等问题不会被宿主 shell 替代而失真。
14. As an 审计工程师, I want 适配只通过预定义模板完成, so that 环境补齐不会偷偷修改认证、过滤或边界检查逻辑。
15. As an 审计复查者, I want 每个适配参数都有来源引用和差异记录, so that 可以判断实验条件是否被证据支持。
16. As an analysis Agent, I want 只使用已核实的 NVRAM API 模板, so that 不会把不同厂商的包装函数误当作同一个 ABI。
17. As an 审计运行者, I want 未知配置值明确成为阻塞, so that 工具不会用伪造成功响应制造误导性行为。
18. As an 审计工程师, I want 每个 Investigation 有独立的会话计数, so that 分析最多开启三个会话且预算可审计。
19. As an 审计工程师, I want 每个 Verification Case 有独立的会话计数, so that 复核最多开启三个会话且不会继承 Analysis 名额。
20. As an 审计工程师, I want 正常对照、异常输入和重复复现都计入执行次数, so that 预算不能通过改名测试绕过。
21. As an 审计运行者, I want 单次执行默认 60 秒且最多 180 秒, so that 普通实验有合理上限并能处理较慢的固件程序。
22. As an 审计工程师, I want 预检不占目标执行次数但计入工具和活动时间预算, so that 准备成本仍然可追溯。
23. As an 审计工程师, I want 失败不会自动原样重试, so that 相同阻塞不会反复消耗 GLM 和工具预算。
24. As an 审计复查者, I want 超时、信号、启动阻塞、运行时依赖阻塞和执行设施失败分开, so that 失败原因不会被混成漏洞反证。
25. As an 审计工程师, I want 超时后清理 QEMU、派生进程和容器, so that 后续实验不会被遗留进程污染。
26. As an 审计复查者, I want 即使清理不确定也保留状态、日志和限制说明, so that 未完成实验不会伪装成正常结果。
27. As an 审计复查者, I want 保存目标、依赖、镜像、QEMU、模板、输入和输出的 digest, so that 实验可以重建和核验。
28. As an 审计复查者, I want 输出截断和上限明确可见, so that 长日志不会静默丢失关键限制。
29. As an verification Agent, I want 能看到原始材料入口但不能直接引用 Analysis 的运行结论, so that独立复核仍遵守 ADR-0012 的 Evidence 规则。
30. As an 审计运行者, I want 现有 gen-0001 保持不变, so that 引入 QEMU 不污染已封存结果。
31. As an 审计工程师, I want 合成夹具和真实固件测试分开, so that 接口契约通过不被误报为真实固件集成成功。
32. As an 审计运行者, I want 看到某个真实固件程序或 CGI 的输入输出、正常对照和干净复现, so that 第一阶段能力有实际业务通路验收。
33. As an 审计运行者, I want NVRAM 模板通过真实接口兼容性测试, so that 模板不会只在合成函数上看似可用。
34. As an 审计复查者, I want QEMU 的成功运行不自动变成漏洞结论, so that 动态观察与安全判定保持清晰边界。
35. As an analysis Agent, I want 会话运行目录内的状态跨 ReAct 轮积累, so that 登录、写配置、触发这类多步通路能在同一会话内完成。
36. As an 审计工程师, I want 会话即执行名额单位且 Host 在调查终态强制停机封存, so that 预算可审计且不依赖 agent 自觉停机。
37. As an 审计复查者, I want 会话台账记录有序的执行声明、输出和 digest, so that Verification 能独立开会话逐条重放。

## Implementation Decisions

### 2026-09-22 执行后端定案：PRoot + QEMU

用户已选择该路线；此前“执行机制未定、暂缓”的决定由本节替代。依据：[PRoot 调查](investigation/proot-arm-chain-2026-09-22/README.md)。所测 ARM 原固件派生链及 MIPS 对照可运行，不代表真实 CGI 业务通路、全部 ABI 或生产隔离已验收。

- Docker 保持隔离边界；每次执行由 PRoot 接续 guest 发起的执行请求并交给 QEMU。会话容器常驻，每次执行新建 PRoot 实例；仅声明的运行文件跨执行保留，目标进程不能跨执行存活。
- 用户后续指定交付目标为 **PRoot 5.4.0 + QEMU 11.1.1**。票 16 构建新版本执行镜像，固定官方源码来源、校验值、基础镜像 digest、构建参数和 ARM/MIPS 产物身份，并先验证完整组合矩阵。已有 PRoot + QEMU 5.2/bookworm-slim 成功结果仅作历史对照；裸 11.1.1 测试不能替代新组合测试，旧 bullseye 镜像也不视为等价。新版组合失败须记录阻塞，不静默回退 5.2 或降低验收；不以版本号推断兼容性提升。PRoot 5.1.0 仅为历史对照，不承诺双版本支持。
- 使用显式运行根和最小 bind 集，不依赖 `-R` 自动绑定。Docker 只读挂载保护原件，运行目录与 Evidence 分离；只暴露必需设备（如 `/dev/null`），不照搬整个 `/dev`。默认 seccomp、无 privileged、无新增 capability 为已测基线；失败报设施阻塞，不自动放宽权限。
- **接入前置闸：**调查已证明 `/host-rootfs` 可供 guest 执行容器原生程序。PRoot 不是安全隔离；顶层参数或路径前缀检查不足以约束固件内部执行。票 16 必须实现并实测运行时约束，拒绝 guest 借该路径或等价别名启动容器原生 shell、工具或额外 QEMU，覆盖规范化、符号链接及适用的 proc/fd 路径和执行系统调用变体。可信后端启动与 guest 自主执行分开授权。若现有约束下做不到，记录阻塞，票 16 不得放开目标执行，不宣称调查已解决隔离问题。
- 预检仍不运行目标、不建会话；补记 PRoot/QEMU/镜像身份及验证矩阵，不能把 ARM 无条件标成支持，也不沿用“所有 ARM 链均阻塞”的旧结论。
- Evidence 区分声明目标、实际固件及依赖 digest、PRoot/QEMU 身份与临时 `prooted-*` 装载桩。桩不是原固件或 QEMU 原件；不能只凭 `/proc/*/exe` 或 cmdline 证明链身份。观测不足须标明，不把进程轮询快照宣称为完整执行链。
- 清理覆盖 PRoot、QEMU、固件子孙进程。停止 Docker 客户端或顶层进程不足以证明清理；无法确认整次执行清理时销毁会话容器并封存，仍无法确认则记录清理不确定。PRoot 临时桩和 bind 残留不隐式进入后续执行或新会话。

### 沿用的能力、预算与证据契约

- QEMU 用户态执行能力放在版本固定的 Docker 执行镜像中，由专用工具覆盖镜像入口调用；不要求宿主 Kali 安装 QEMU，不依赖宿主 binfmt。镜像可以复用现有沙箱的基础层，但 QEMU 工具必须有独立入口和能力契约。
- 首批架构矩阵以 ARM32 little-endian/uClibc 与 MIPS32 big-endian/musl 为目标。具体 QEMU 二进制、解释器前缀、动态库可解析性和 ABI 兼容性必须在技术前置调查中实测；不能据架构名称宣称所有程序可运行。
- 提供预检与会话两组外部行为能力。预检只检查 ELF 架构、解释器、依赖、模板适用性和路径边界，不执行目标也不创建会话；会话能力按生命周期运作：开启会话按声明创建干净副本，会话内每次执行运行目标与有限子进程链并采集结构化结果及原始输出，停机或强制封存时拆除容器并生成会话台账。
- QEMU 工具与 `sandbox_verify` 共享容器隔离、网络断开、超时、输出截断和 Evidence 写入基础；脚本工具不能调用 QEMU 或其他固件目标执行入口。若共用镜像导致能力无法隔离，应拆分执行镜像而不放宽入口。
- 固件解包树、目标 ELF、加载器和固件库默认只读。每次会话拥有独立可写运行目录，目录内状态跨轮积累；程序写入的运行文件属于实验输出，不是权威 Evidence。Host 在执行结束后读取并摘要，Evidence 原文不可由目标进程修改。
- 默认网络为断网，不挂载 Docker socket、其他 target、宿主全局 binfmt 或无关宿主目录。QEMU 的 loader prefix 只负责解析目标解释器和库，不能代替文件系统隔离。
- 输入契约至少包含目标工具路径、运行根、argv（含 argv0）、工作目录、受控环境、stdin/输入文件、适配模板参数和每个参数的来源引用。宿主环境变量不隐式继承；测试输入和“设备真实配置”分开记录。
- 环境适配只使用预定义模板。基础目录、配置文件、参数和 CGI 输入属于第一批模板；NVRAM 只在函数原型、调用约定、返回值、缺失键语义和来源值已核实后进入支持表。target/6 与 target/7 的 NVRAM 包装层分别建模；target/8 暂不列为 NVRAM 模板样本。
- 有限子进程链指目标程序启动的固件内 shell/辅助程序，仍受进程数、路径白名单、运行时间和总预算限制。宿主 shell 不能替代固件 shell；独立顶层目标执行不能藏在脚本批处理中。
- 结果分类至少包含正常退出、非零退出、目标信号/崩溃、超时、准备阻塞、运行时依赖阻塞、执行设施失败和清理不确定；保留原始退出码、信号和日志。工具不返回漏洞成立/不存在。
- 时间预算：每次目标执行默认 60 秒、硬上限 180 秒；执行名额按会话计，Analysis Investigation 最多 3 个会话，Verification Case 独立最多 3 个；会话内执行次数上限为显式预算参数（随 QEMU 预算块走既有分层解析，`.env` 环境层可覆盖，缺失或非法值回落默认），临时默认值 4，最终默认值由真实样本校准定稿；不另设会话级活动时长上限，活动时长由执行次数与单次超时自然封顶。正常对照、异常输入和复现均为会话内执行，逐条计入台账并计入案例活动时长预算；预检不占执行名额但计入工具调用与活动时间。失败不自动原样重试。
- Host 增加按 Investigation/Verification Case 持久化的目标执行台账，并在开始、完成、超时、中断、清理和恢复时更新。配置快照记录生效值、来源和版本；恢复不能重复计算已经持久化的执行。
- 超时和中断必须终止并确认容器及派生进程状态；无法确认时结果为清理不确定并保留日志，不能标为正常退出或安全反证。调查无论正常完成、预算耗尽还是中断，Host 都强制停机并封存全部开启会话，不依赖 agent 自觉调用停机；恢复路径对遗留容器强制收割。中断即会话死亡：恢复不复活被中断会话，其运行目录产物留档供复查但不进入新会话；续跑开启新会话，已持久化的执行不重复扣名额。执行入口必须避免只依赖宿主客户端进程退出。
- 每次会话生成可复查材料：会话身份、角色和 Investigation/Case 归属、目标与依赖 digest、镜像/QEMU/template 版本、规范化输入、适配来源、限制值、实际耗时、状态分类和清理结果；会话台账按序记录每次执行的声明输入、原始输出与 digest。
- analysis 可以将 QEMU Observation 作为 Evidence，提出 Claim 或后续动作；verification 必须独立开启会话、按台账重放关键执行序列来重新取得关键观察。Host 按 ADR-0012 聚合 Claim，不因 QEMU 返回 0 或崩溃自动产生 Finding。
- 真实固件通路、正常输入对照、干净环境重复、有限 NVRAM 真实接口、缺依赖/未知配置、信号/超时/中断、输出上限和独立复核共同构成第一阶段验收。安装成功、版本输出、合成夹具成功或单个程序启动不单独满足交付门槛。
- 既有 sealed run 不迁移、不重写、不用 Ground Truth 驱动 QEMU 输入。新能力只在显式新运行世代中评价；审计质量改善另以固定条件对照测量。

## Testing Decisions

`test_binfmt_independence_control` 是无 ARM binfmt 环境下的裸跑否定对照。若执行容器所在内核已注册 ARM binfmt，该前提不成立；测试应说明环境原因并记为未验证，不能将跳过计作通过，也不能将自动转译后的退出码改为可接受值。当前环境继续真实验证正式 PRoot + 容器内 QEMU 执行链；无 binfmt 对照待独立环境补测，不要求修改宿主全局注册，不阻塞票 18。记录两类证据各自证明的范围。

票 16 在一次执行内贯通并复现 ARM 原 shell→原动态程序、原静态辅助程序及 MIPS 对照，并验证 `/host-rootfs` 绕过拒绝、只读材料和清理。同票覆盖非 shell 父程序的直接派生及短命子进程观测；票 18 验收真实业务通路，票 19 校准和收口。机制探针不能替代后续验收；调查中的权限、清理和耗时结论不推广到未经测试的部署环境。

好测试验证外部行为和可复查工件，而不是某个 QEMU 命令拼接的内部实现。所有不需要真实架构执行的测试使用确定性模型、Docker 调用替身和临时工作区，不调用真实 LLM，不消耗 GLM 额度。

测试接缝按两层组织：

1. **离线 Host→专用工具→Evidence/恢复接缝**。验证参数校验、路径白名单、能力授权、脚本不能调用 QEMU、目标执行计数、Analysis/Verification 独立预算、预检不占名额、失败不自动重试、配置快照、事件恢复、结果分类、输出截断、原始输入只读、运行目录与 Evidence 分离，以及中断/超时后的状态。
2. **Docker＋QEMU＋真实固件集成接缝**。验证镜像内 QEMU 版本和架构选择、target/6 或 target/7 的真实单次程序/CGI 通路、有限子进程链、正常输入对照、干净重建、target/6 或 target/7 的真实 NVRAM 适配，以及至少一个 MIPS32 big-endian 样本的真实执行（实际运行并取得结果分类与输出，预检不计入该项验收）。集成测试必须在依赖缺失时明确跳过并记录原因，不能静默假绿。

应复用现有 Host driver、budget、tool contract、Docker runner、tool recovery、Evidence 和报告测试的公开 seam；新增测试应通过工具替身验证确定性控制，通过现有 Docker 门控模式验证真实容器行为。测试应覆盖：

- 目标执行成功、非零退出、目标信号、超时、准备阻塞、运行时依赖阻塞、执行设施失败和清理不确定；
- 会话生命周期：开启/执行/停机的正常路径，调查完成、预算耗尽、中断各终态下的强制停机封存，恢复路径对遗留容器的强制收割，以及中断即会话死亡语义（恢复不复活会话、留档不进新会话、已持久化执行不重复扣名额）；
- 有限 shell/辅助程序的子进程数量和路径限制，以及一次脚本不能批量产生多次顶层 QEMU 执行；
- Analysis 三个和 Verification 三个会话的独立计数、会话内执行次数上限记账（显式参数，含 `.env` 覆盖与缺失/非法值回落）、对照/异常/复现计数、案例总预算耗尽和恢复后的不重复计数；
- NVRAM 已知值、缺失键、未知值、未支持 ABI 和 target/6/7 包装接口差异；
- 目标写运行目录但无法写解包树、历史 Evidence 或其他 target；
- 中断发生在启动、输出、完成和清理各边界时的持久化状态与恢复行为；
- 真实固件通路有输入输出和正常对照，第二个会话不继承第一个会话的运行文件，同一会话内后继执行可见前序执行写入运行目录的状态，Verification 按台账重放但不直接复用 Analysis 的会话产物；
- 合成夹具只证明接口契约，不能替代真实固件集成验收。

## Out of Scope

- 不安装或依赖 Kali 主机全局 QEMU、binfmt 或宿主架构模拟配置。
- 不做 QEMU system/full-machine 模拟、内核启动、设备树、真实网卡、常驻 HTTP 服务或跨固件网络拓扑。
- 容器生命周期与会话一致：会话期内容器跨工具调用存活，会话结束即拆除；不保留跨会话容器，不把一个容器作为多个固件或多个调查的共享运行环境，两次执行之间不允许目标进程存活（常驻网络服务属后置范围）。
- 不自由生成替代库、厂商 NVRAM 实现、认证绕过、输入过滤修改、边界检查修改或其他与漏洞成立有关的程序补丁。
- 不把未知 NVRAM API、未知配置值、启动失败、崩溃、退出码或字符串单独解释为漏洞成立或漏洞不存在。
- 不允许 `sandbox_verify` 作为 QEMU 批量执行后门，不允许模型自由拼接任意 Docker/QEMU 命令。
- 不要求第一阶段支持全部固件、全部 ARM/MIPS ABI、target/8 的 NVRAM 模板、所有 CGI 或所有真实设备服务。
- 不改写或迁移既有 sealed run，不把 Ground Truth 暴露给 Agent，不以命中 GT 作为 QEMU 集成验收条件。
- 不在本规格范围内解决 LLM 客户端超时、GLM 模型额度或真实审计质量基准；这些由现有运行和独立评估流程处理。

## Further Notes

Q7 和 Q8 的决定已写入 ADR-0013：第一阶段包含有限的固件子进程链；交付必须包含真实固件单次程序或 CGI 通路、正常对照、干净复现和真实 NVRAM 接口兼容性。QEMU 运行成功仍只是固件执行实验的 Observation，最终安全结论继续由独立 verification 和 Host 的 Claim 门槛决定。

实现前需要把尚未核实的事项作为有明确产出的前置工单：镜像中 QEMU 的固定版本和 ARM/MIPS 二进制可用性、真实样本通路选择、NVRAM ABI/缺失键语义、子进程执行与清理机制、资源上限的最小样本校准。不能把这些调查结果预先写成“所有样本支持”。

2026-09-21 规格访谈第二轮确认：执行模型为会话制——会话运行目录状态跨 ReAct 轮积累，会话之间干净重建，一次性单发实验是只含一次执行的会话特例；容器生命周期与会话一致，会话结束即拆除；第一阶段不含常驻网络服务，两次执行之间不允许目标进程存活；调查各终态由 Host 强制停机封存，不依赖 agent 自觉停机；中断即会话死亡，恢复不复活会话、已持久化执行不重复扣名额。

本规格使用 `ready-for-agent` 标签发布；工单已生成。2026-09-22 按用户确认将剩余工作重组为票 16–19，旧 06–15 保留历史并停止单独调度，见 [实施顺序](execution-order.md)。生成的工单无需再次 triage，后续按阻塞关系逐票实现、测试和 code-review。本次文档同步不代表产品实现已完成。

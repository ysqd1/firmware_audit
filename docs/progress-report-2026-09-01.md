# 机器人固件安全审计流水线 · 项目进展汇报

> 汇报日期：2026-09-01 ｜ 研究对象：Unitree 机器人固件（AirPro EDU 定制包 v1.1.7 等）
> 阶段定位：Step0–Step5 全流水线已落地并完成首轮端到端验证，处于"单机型单固件验证 → 通用化与验证能力补强"过渡期

***

## 一、项目背景与目标

### 1.1 研究背景

消费级/行业级机器人固件是攻击面的"低洼地"：厂商大量使用交叉编译的 aarch64 二进制、内核模块、设备树与专用恢复镜像，且普遍缺乏签名与完整性机制（本次审计即在目标固件中确认了 `cskburn` 烧录器无完整性校验、多进程无栈保护等事实）。固件一经出厂便难以升级修补，静态审计成为识别硬编码凭据、命令注入、供应链风险的唯一低成本入口。然而传统工具链（binwalk / Ghidra / checksec / cve-bin-tool 等）工具多、联动少、结果靠人肉归并，审计一版固件往往以"人月"计。

### 1.2 核心目标

1. **端到端自动化**：构建"输入一个固件（归档 / 单文件压缩 / GB 级磁盘镜像）→ 输出一份结构化审计报告"的流水线；
2. **LLM Agent 智能审计**：以 ReAct 模式的三层 Agent（侦察→分析→复核）替代人工归并，用 LLM 做推理大脑、用确定性代码做硬约束；
3. **针对性适配**：面向机器人固件特有的输入形态（U-Boot / DTB / 内核模块 / 专用恢复镜像 / rootfs，以及大至数百 GB 的整盘镜像）给出可用的处理路径；
4. **可复现与可追溯**：每个阶段产物 JSON 工件化、断点续跑、审计指纹留痕，坏结果如实标注（degraded / 未复核），绝不冒充成功。

### 1.3 当前阶段

- Step0–Step4（解压/分区 → 解包 → 过滤 → 分类 → 反编译/提取）已实现并跑通真实固件；

- Step5 Agent 层已演进到 v3（LLM orchestrator 编排 + 三子 Agent），实测首轮端到端完成并暴露/修复多类真实缺陷；

- 测试面：pytest 全量 176 用例通过（2026-08-29 报告），真机 LLM smoke 3 项通过，Docker 门控 8 项视环境跳过；

- 目前的**主要开放问题**集中在：①Step2 过滤的通用性；②动态验证能力缺失；③Agent 层成本与真实性校验。

## 二、已完成工作（分步骤）

### 2.1 Step0：输入分流与磁盘镜像分区提取

**职责**：识别固件形态，分流到正确路径。

| 输入形态                 | 处理路径                                                 |
| -------------------- | ---------------------------------------------------- |
| 归档（zip/tar\*/tar.xz） | 宿主 Python 预解压 → 引导解包器树扫描（scan\_tree）继续解嵌套容器，失败回退直接用树 |
| 单文件压缩 / 其他           | 交引导解包器单文件模式，失败回退 binwalk -Me                         |
| 磁盘镜像（GPT/MBR, 数百 GB） | 解析分区表 → 每个分区独立子工作区递归跑 Step1–4                        |

**分区准确性防线**（宁可拒绝、不可静默出错）：sfdisk（libfdisk 权威实现）主解析 + 手写解析（CRC32 强校）回退；分区边界检查；按分区名推断 kind 与头部签名交叉验证；提取后回读校验（不一致即删除）；复用同样过回读校验。实测 g1 镜像 15 分区：默认提取 6 个（kernel×2、recovery×2、esp×2），dtb ×4 / reserved ×3 / 237GB rootfs 合理跳过。

### 2.2 Step1：引导式解包

以魔数决策（`file_magic.py` 纯函数）逐层决定拆什么、用什么工具，重点解决 binwalk 递归解包的三大痼疾：嵌套容器（解出的内层 tar/镜像继续解）、Python SDK 等第三方容器噪声（跳过 botocore 等零价值目标）、脏目录断点续跑（`.step1_done` 标记 + manifest 续解）。实测处理过 61.6 万条目的 DTB 分解树，并解决了遍历慢被误判死机的问题。

### 2.3 Step2：白/黑名单过滤（详见"当前问题 · 3.1"）

只保留该审计的内容：厂商定制目录（home/unitree、内核模块）与 etc 敏感配置为白名单强制保留；usr/share、lib、usr/local/lib（Python SDK）等系统目录黑名单排除；前置排除 DTB 节点分解噪声（`name@addr` 路径，数十万级）与构建产物；双副本去重（binwalk 同一逻辑文件两份拷贝）+ ELF 内容级去重（`.so/.so.N` 同内容只留基础名，实测 16 组 17 个，单库 Ghidra 268s 减半）。名单外置 `profiles/nano-ubuntu.yaml`，并提供"白名单 0 命中"健全性告警。

### 2.4 Step3：分类

按文件实际类型（ELF / 脚本 / 源码 / 配置 / 文本 / 各类证书与密钥 / 未知）硬编码分类，不用 LLM；结果写入 FileInfo 并供 Step4/Step5 使用。

### 2.5 Step4：反编译/提取

- ELF → Ghidra Headless 容器并行（Docker 精简镜像，体积降 62%；`-analysisTimeoutPerFile` 限时），产出反编译 C + functions/imports/symbols/strings/meta/text/crypto 多视图 JSON，统一进 `analysis/` 合并目录；

- 文本/脚本/源码 → 规则化敏感信息扫描（URL/IP/口令/私钥等，识别"疑似"并保留证据指针）；

- 证书/密钥 → 按 crypto\_\* 类型解析（系统信任库与厂商硬编码凭据区分标记）；

- 透明 vs 不透明分诊（`triage.py`）：对 binwalk 解不开的 `flashboot/master/respak/script` 类不透明固件走熵/魔数分诊，不盲目解包。

### 2.6 Step5：LLM Agent 审计（v3，本轮工作重心）

**架构**：`Orchestrator`（LLM 编排，3 个动作 `dispatch_agent/summarize/finish`）+ 三个 ReAct 子 Agent（recon → analysis → verification），阶段顺序单向、类型+任务唯一、调度次数上限均由**代码硬约束**而非依赖 LLM 自觉。

| Agent           | 工具集                                                                                                                   | 轮上限      | 输入 → 输出                                             |
| --------------- | --------------------------------------------------------------------------------------------------------------------- | -------- | --------------------------------------------------- |
| recon 侦察        | list\_files, read\_file, cve\_bin\_tool\_scan, semgrep\_scan, gitleaks\_scan, binwalk\_rescan                         | 20       | Step4 工件 → `survey.json`（v3，架构快照/入口/观察点/扫描建议，无判级字段） |
| analysis 分析     | 12 个（search\_code/find\_decompiled\_function/xref/imports/strings/checksec/cve\_lookup/semgrep/gitleaks/web\_search…） | 30       | survey.json → `findings.json`（候选漏洞+证据链）             |
| verification 复核 | read\_file/checksec/xref/cve\_lookup/sandbox\_verify…                                                                 | **8/实例** | 单条 finding（前 K 条之一）→ 复核结论（verified=true/false/null） |

**v3 关键设计（ADR-0001\~0006）**：

1. **verification 每疑点一实例（ADR-0003）**：analysis 的 findings 按 severity+confidence 取前 K 条（env `STEP5_VERIFY_K`，默认 10），逐条独立实例复核，单实例 max\_iters=8；聚合回 `verified_findings.json`（全量 N 保留：前 K 带结论，未进 K/实例失败的 `verified=None` 划入报告"⚠ 未复核区"，与复核误报（false）严格区分——"没复核"不等于"已否"）；补跑逻辑整体取消，阶段只调度一次，单向顺序门防重复。
2. **token 截断续写（ADR-0005）**：推理模型 `reasoning_content` 烧满导致 content 为空时，把 reasoning 拼回请求续写一次（"直接给最终答复"），不再当空回复硬重试；续写只回传 API、不进 ReAct 上下文。
3. **ReAct 工程化（循环守卫）**：纯文本协议 + 解析失败回喂纠错（≤2 次）；同参空转拦截（第 4 次起不执行、回喂干预）；零工具调用禁止直接 Final（拒绝退回后放行防死锁）；迭代上限三层提示（每轮进度 / 最后一轮总结要求 / 强制收尾）。
4. **上下文与证据管理**：四分区上下文（系统提示/简报永不压缩、概括区滚动压缩、保留区最近 K 轮），600k 字符阈值触发压缩；Observation ≤8KB 头尾保留截断，**全文落盘** `obs/step<N>_<tool>.txt`，LLM 可 `read_file` 分页回读省略段。
5. **断点续跑与留痕**：`.json` 工件存在 → skipped；仅 `.md` 降级 → degraded（默认复跑）；orchestrator 目录留 `transcript.jsonl + dispatch_log.json + handoff_<seq>_<type>.json + report.md + result.json`。

**首轮真实端到端结果（target/1，`custom_package_AIR_PRO_EDU_1.1.7_mod_1.0.tar.xz`）**：

- 编排过程：recon 1 实例（识别 55 个 ELF + 964 个脚本）→ analysis 3 次调度（动态分配，单实例 25–29 步，累计 903s，产出 8+ 条候选）→ verification 每疑点实例；

- 捕获的真实安全问题（已复核或 analysis 高置信初值）：`bashrunner.py` DDS 命令注入（critical）、`set_remote_id.sh` sudo 参数注入（critical）、`assistant_recorder` 无认证文件写入（high）、`chat_go` 硬编码阿里云/AWS API 密钥（high）、`cskburn` 烧录器无完整性校验且无栈保护（high）、`idlc` dlsym/dlopen 加载用户可控路径（medium）、`net_switcher` subprocess（medium）等；`webrtc_bridge` 认证薄弱一条经复核判定为误报（证据链完整：唯一 auth 命中来自 zstd 库错误消息，非认证代码）；

- 暴露并修复的真实缺陷（详见 test-fix-reports）：verification 实例加载 `Finding` 缺 `title` 参数致复核失败、Final Answer 解析取首个标记污染报告头部、step5\_run LLM 用量恒为 0、协议纠错文案误导收尾阶段——修复后编排轮次 10→6、端到端 token 63.3k→26.5k（-58%），report.md 首行干净。

## 三、当前存在问题分析

### 3.1 Step2 过滤：设计合理性与通用性问题

**现有实现方式**：双层名单（白名单强制保留 → 系统标准/黑名单排除 → 其余默认放行交给 Step3）+ 三类前置降噪（DTB 节点路径、构建产物、去重）+ 名单外置 YAML + 健全性告警。

**合理性（在单机型前提下的优点）**：

- 白名单优先于黑名单，保证"降噪不误伤定制内容"；构建产物过滤带"优先于白名单"语义，避免整数保护被垃圾稀释；

- ELF 内容去重收益明确（同内容 `.so` 副本只留基础名，Ghidra 时间减半）；

- 拒绝语义外溢：双副本按（逻辑路径+哈希）去、同名不同内容的 ELF 不去重（防语义损失）；

- `sanity_check_whitelist` 对 binwalk 命名结构变化导致的"静默白名单 0 命中"给出显式告警。

**局限与通用性风险**：

1. **强先验依赖**：白名单（home/unitree）、敏感 etc 清单、`usr/lib` 等黑名单均为宇树 nano（Ubuntu Buildroot）型号的手工归纳。换 Yocto 或其他厂商固件时路径完全不同，可能全放行或全误删；健全性告警只能"提示"不能"自愈"。
2. **路径模式匹配脆弱**：匹配基于"逻辑路径剥 binwalk 前缀"的字符串操作，固件解包结构/工具链版本一变即静默失效；纯子串模式（如 `.map` 误伤 .NET settings.map，已修复并注明"收益小风险大"）表明模式通用性与准确性的天然矛盾。
3. **内容级判断缺位**：除 ELF 去重外，过滤基本不看内容。`usr/local/lib` 一次实测 2101 个文件"零价值"的结论建立在"第三方 SDK 恰在标准路径"这一先验上，换一个 SDK 布局即失效。
4. **决策黑盒**：过滤只输出保留/剔除二元结果，不落 `filter_reason`，事后无法解释"为什么这个文件被排除"，调参只能靠重跑对比。
5. **与 Step3/Step4 职责耦合**：`file_rules.py` 虽已收敛系统标准/信任库/搜索过滤三类名单，但"哪些文件送审、怎么审"的判定链条仍跨 Step2–4，测试需同步维护 profile。

**改进方向（初步）**：①发行版系统文件识别内容化——rootfs 自动识别发行版后，用官方软件包 manifest 比对替代路径黑名单；②引入语义价值排序——ELF 按符号规模/字符串密度/导入危险函数度排序，过滤只做"优先级"不做"生死"；③过滤理由落盘（fileinfo 增 `filter_reason`）；④profile 定位从"唯一真相"降级为"种子覆盖层"，由统计特征自举补齐。

### 3.2 动态验证与挖掘机制：实现方案探讨

**现状与缺口**：当前验证以静态为主。verification 的 `sandbox_verify` 只支持 python/node/php 白名单解释器（extracted 只读、网络隔离、超时），走"提取函数+Mock 依赖+Fuzzing Harness"路线。对**交叉编译 aarch64 ELF 几乎无效**——沙箱是 x86，固件进程无法直接运行，`cskburn`、`idlc` 等关键二进制只能靠 imports/checksec/xref + 代码推理判定。首轮复核实例的观测记录也显示大量实例以 read\_file/checksec 为主，`sandbox_verify` 未被实际使用——工具能力与 Agent 行为之间存在落差。

**动态运行环境构建方案（分层，按投资回报排序）**：

| 层级             | 手段                                                      | 覆盖目标                                    | 输入/输出方式                                                                 | 结果验证方法                                      |
| -------------- | ------------------------------------------------------- | --------------------------------------- | ----------------------------------------------------------------------- | ------------------------------------------- |
| L1 脚本层（已有）     | 隔离容器 + 解释器白名单                                           | Python/Node/PHP 服务（bashrunner 等 DDS 入口） | 注入源码 + 构造 DDS/参数 payload → stdout/退出码                                   | 断言规则 + LLM 归因（是否触发 system/写文件）              |
| L2 用户态模拟（推荐优先） | `qemu-aarch64-static` + seccomp syscall 白名单 + ptrace 追踪 | 无硬件依赖的二进制（cskburn、idlc、ox-roudi）        | argv/stdin/环境注入，QEMU LD\_PRELOAD 式桩替 libc 危险调用 → syscall 序列 + exit code | 破坏性 syscall（execve/socket/bind）是否达、是否受控输入触发 |
| L3 消息面仿真       | 沙箱内 mock DDS/DBus 双端                                    | 机器人主通信链（评估 cyclonedds 体系）               | 按 IDL 构造消息 → 触发目标服务处理函数                                                 | 观测目标进程行为（写文件/命令执行/崩溃）                       |
| L4 全系统仿真       | QEMU full-system + 精简 rootfs                            | 起机流程、内核模块、网络/OTA 入口                     | 磁盘镜像 + serial console → 服务日志                                            | 按入口白名单验证网络可达面，成本最高、按价值挑选                    |

**关键设计问题**：

- **输入输出规范**：保持 AgentTool 契约不变，新增 `sandbox_dynamic(file, inputs, harness_code, arch)` → `ToolResult(data={exit_code, syscall_trace, mutated_output})`，Agent 与代码双通道判真；

- **结果可信度**：动态输出必须可溯源（payload、命令、时间戳），"无输出/崩溃"也是证据而非失败；

- **验证优先级**：只对 analysis 判 high+ 且存在明确触发面（DDS 消息/CLI 参数/网络端口/文件输入）的疑点做动态验证；无可触发面者（硬编码密钥等）写明静态判定依据即可；

- **验收集**：建议引入动态确认率/总复核比与误报率两个指标，作为"该不该为某类漏洞投入动态验证"的量化依据。

### 3.3 架构设计不足与优化建议

1. **验证深度与成本错配**（本轮最值得反思的问题）

   - 现状：verification 每疑点独立实例但只有 8 轮，且复核工具用例单一（首轮几乎全是 read\_file/checksec）；"一实例一体检、跑完即止、不复验不接力"虽保证语义干净，但对 code 类疑点深度不足。

   - 建议：按疑点类型分配验证策略（脚本类直接跑 harness；ELF 类走 L2 模拟；纯静态类走"证据链完整性检查"），并给实例配"第二意见"选项（同疑点两次独立验证取交集）——以"低估漏报、不冒充"为红线，成本由 K 值与时控共担。

2. **编排成本不可控**

   - 现状：analysis 动态补跑由 orchestrator LLM 判断，首轮实际跑了 3 次（第三次耗尽 30 轮 903s 才收尾）；端到端 token 波动大（63k→26.5k）。

   - 建议：把"预算"做成显式资源（每阶段计时/token 预算注入 budget\_state），LLM 在预算内决策；口径与 result.json 的 `budget` 字段统一，便于事后分析。

3. **报告真实性校验缺失**

   - 现状：report.md 由 orchestrator LLM 依据 summarize 素材生成，但实测出现过 report 叙事与 verified\_findings.json 工件不一致的情况（报告声称与工件计数对不上）。

   - 建议：落盘前对 report 做**素材一致性检查**（报告内 finding 集合 ⊆ summarize 素材集合、verified 计数 == 工件计数），不一致则拒绝落盘并告警（复用 degraded 语义）。

4. **Ghidra 计算瓶颈**

   - 现状：单库最大 `libddsc.so` 268s、4 并行容器、61.6 万条目树遍历是时长主要开销；反编译结果不可跨版本复用。

   - 建议：反编译缓存指纹化（ELF sha256 → 产物），跨 run/跨分区共享；`max_elf`+价值排序（优先高符号/危险导入库）作为首选项。

5. **可复现性与实验管理**

   - 提示词/模型/工具集组合无统一"审计指纹"；两轮实验结果无法快速 diff。

   - 建议：把"配置 hash + 组件版本 + LLM 参数"写入 report/result.json 头；Agent prompt 全部留档（已有 system\_prompt.txt，补 hash 绑定）。

### 3.4 其他技术难点 / 理论问题

1. **交叉编译反编译的语义鸿沟**：Ghidra 反编译 C 与真实实现存在翻译误差，LLM 依据反编译代码下结论需证据链（地址+调用点）锚定，防"还原度幻觉"。
2. **LLM 幻觉治理**：finding 必须带 file+addr/func+证据片段，否则拒绝入链；recon v3 明确禁止依据记忆填写 CVE/版本（只认工具 Observation 实况）。
3. **大镜像 I/O 与磁盘**：237GB rootfs 跳过是成本决策，但"跳过整个 rootfs"可能漏掉系统级供应链风险——需产出显式的未审计面声明。
4. **CVE 匹配噪音**：cve-bin-tool 对嵌入式交叉编译库误报偏多（已在工具层可选化），需要"版本→产品"归一化后的置信度过滤。
5. **合规与披露**：审计日志/报告存在泄露真实密钥与 POC 的风险，涉及负责任披露流程与实验环境隔离（沙箱断网、样例库脱敏）。

## 五、需要导师指导的问题清单

> 每条均附**我的初步思考**，便于导师直接评估或纠偏。

**Q1 动态验证的投入边界**：固件审计中硬编码密钥/签名缺失类无法"动态触发，静态判定"即可，命令注入/参数注入类才值得动态验证。如何更系统地确定"哪类疑点该投动态验证、投入多少"？

- 初步思考：以"存在明确触发面（网络/DDS/CLI 参数/文件输入）+ severity≥high + 静态证据不足以定论"为触发条件；用动态确认率/召回率数据回退校验该边界。

**Q2 Step2 通用化路线**：内容特征过滤 vs 发行版软件包清单比对，哪条路更符合工程实际、两者如何组合？

- 初步思考：先做"发行版识别 + 系统文件特征库（哈希/路径统计）"作通用底座，profile 降级为机型覆盖层；语义价值排序（符号/字符串密度/危险导入）作第三层。想请教导师对"特征库维护成本 vs 路径先验维护成本"的判断。

**Q3 准确率评价方法**：没有 ground-truth 的固件审计（真实厂商固件），如何评估 recall/precision？是否应像安全研究惯例那样用"已知漏洞固件基准集"来标定？

- 初步思考：拟收集 3–5 个含已知漏洞的公开固件/CTF 类目标做对照，同时引入人工抽检口径（verification 过滤后按比例人工复核，上报一致率）。求导师对基准集构建与抽检比例的建议。

**Q4 仿真投入的 ROI**：QEMU 用户态模拟（L2）与全系统仿真（L4）的优先顺序？

- 初步思考：先 L2（无硬件依赖、见效快），L4 只对网络/OTA 入口做。想确认导师对"机器人固件审计以静态为主、动态为辅"的整体定位是否认可。

**Q5 Agent 预算与成本**：orchestrator 由 LLM 自主调度导致成本波动较大（端到端 token 63k→26.5k 区间）。是否应该引入显式预算上限（时间/token）并在超限时降级为"静态深挖"模式？

- 初步思考：建议把预算做成显式资源注入 LLM 决策，超限走"已知收尾"而非无限重试；同时考虑把分析轮上限 (30) 与 token 联动。

**Q6 算力与资源**：Ghidra 并行容器数与内存限制的合理配置；是否有必要上 GPU 或更大的机器来支持半系统仿真/批量固件对比？
